# Contributing

Thanks for taking a look. This card visualises data from
[EVCC](https://evcc.io/) in Home Assistant, and it is built against exactly one
integration: [ha-evcc](https://github.com/marq24/ha-evcc) (`evcc_intg`) by
@marq24. Every entity name, service and WebSocket command comes from there, and
a patch that targets anything else cannot be merged here.

## The one rule

**Edit `src/`, never `dist/evcc-card.js`.**

The bundle in `dist/` is generated by Rollup and committed, because that is the
file HACS ships. A change made directly in `dist/` is silently overwritten by
the next build, and CI rejects a pull request whose committed bundle does not
match `src/`.

```bash
npm ci          # once per clone, installs Rollup
npm run build   # src/ -> dist/evcc-card.js
npm run watch   # rebuild on save
```

## Getting set up

You need Node and npm, Python 3, Chromium and Playwright. On Debian or Ubuntu:

```bash
bash test/setup.sh   # idempotent, checks first and installs only what is missing
npm ci
```

Then confirm everything works:

```bash
npm run build && python3 test/run.py
```

## Project layout

```
src/
  index.js               Entry point: customElements.define, console banner
  evcc-card.js           class EvccCard, lifecycle and config, mixin assembly
  evcc-card-editor.js    class EvccCardEditor, the visual editor
  core/                  constants.js (FEATURES, version), entity-discovery.js, evcc-api.js
  views/                 One mixin per card mode
  components/            soc-control.js (sliders, direct input, boost)
  utils/                 state.js, format.js, html.js, translations.js
  listeners.js           _attachListeners
  styles.js              _styles
dist/
  evcc-card.js           Built bundle (committed, shipped by HACS)
  locales/*.json         Translations, loaded at runtime
test/                    Playwright suite, unit tests, fixtures (see test/README.md)
images/                  README screenshots, generated by test/screenshots.py
```

It is vanilla JavaScript with Shadow DOM and template literals. No framework, no
build step beyond bundling, no minification, so the shipped file stays readable.

Every view, component and helper module exports a plain object of methods that
is mixed into `EvccCard.prototype` at the end of `src/evcc-card.js`. Methods
call each other through `this`. Two mixins may not define the same method name;
that throws at load time rather than silently overwriting.

## Running the tests

```bash
python3 test/run.py                   # everything, Chromium
python3 test/run.py --browser webkit  # the same checks in Safari's engine
python3 test/run.py --only unit       # one group, repeatable
python3 test/run.py --headed          # watch it in a window
node --test test/unit/                # the unit tests on their own
```

The suite runs the card against a mock `hass` fed from JSON fixtures, so no Home
Assistant instance is involved. It asserts on the service calls and WebSocket
commands the card issues, which the mock records instead of executing.
`test/README.md` documents the groups, the fixtures and how to derive variants
from them.

Please add a scenario for what you change. A new interactive control belongs in
`contracts` (it must call the right service with the right payload), a new
render path in `render`, a pure helper in `test/unit/`.

## The pre-commit hook

Activate it once per clone:

```bash
git config core.hooksPath .githooks
```

When a commit touches `src/` or `dist/`, the hook rebuilds the bundle, runs a
syntax check, regenerates the README screenshots and adds whatever changed to
the commit. It takes about 40 seconds and prints nothing in most editors while
it runs, so commit from a terminal if you want to watch it. `git commit
--no-verify` skips it.

## Common tasks

**A new entity.** Add it to the `FEATURES` array in `src/core/constants.js` with
the right `suffix`, `domain`, `type` and `lp` flag. Entities follow ha-evcc's
pattern `<domain>.evcc_<name>_<suffix>`, for example
`sensor.evcc_<loadpoint>_charge_power` or the site-level `sensor.evcc_pv_power`.
Verify in the ha-evcc source that the entity actually exists; the nightly CI job
checks the whole array against upstream and will catch an invention.

**A new mode.** Add `src/views/<name>-view.js` exporting a methods object,
import it in `src/evcc-card.js`, add it to the `mixins` list and add the branch
in `_render`.

**User-facing strings.** Add the key to all files under `dist/locales/`.
`en.json` is the reference; the `locales` test group fails on a missing key in
any language and on a raw key reaching the DOM.

**A new version.** Bump `EVCC_CARD_VERSION` in `src/core/constants.js` and
`version` in `package.json` at the start of the work, then build.

## Opening a pull request

CI runs three jobs on every pull request:

| Job | What fails it |
|---|---|
| Test suite (chromium, webkit) | A failing check, or a committed `dist/evcc-card.js` that does not match `src/` |
| README screenshots up to date | A card change committed without regenerating `images/` |
| Entities exist in ha-evcc | A `FEATURES` entry with no counterpart in the integration |

So before you push: build, run the suite, and if the card's appearance changed,
regenerate the screenshots with `python3 test/screenshots.py --out images` (the
pre-commit hook does this for you).

Describe what the change does for someone using the card, and mention which
ha-evcc version you tested against.
